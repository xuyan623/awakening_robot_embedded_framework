# 公共通信基础设施技术方案（规划阶段）

## 0. 文档目的与范围

本文在不进入接口定义的前提下，细化公共通信的基础技术设施/脚手架搭建方案。  
目标是给出工程实践可执行的设施清单、能力边界、取舍逻辑与落地顺序。

> 本文是技术方案文档，和 `公共通信重构总纲.md`（治理文档）、`分册1_公共通信中间件设计.md`（架构分册）、`公共通信工程落地规划.md`（工程规划）分离存放。

本文覆盖：

1. 数据结构设施
2. OS 基础设施
3. 同步与并发设施
4. 异步执行设施
5. 控制平面治理设施
6. 可靠性/流控设施
7. 可观测与韧性设施
8. 验证与发布设施

本文不覆盖：

1. 结构体、函数、枚举、参数设计
2. 具体代码实现与板卡适配细节

## 1. 设计基线与工程约束

1. 中断路径最小化：中断只做最小可审计动作。
2. 控制平面与数据平面分离：策略治理不侵入快路径。
3. 可观测旁路化：观测设施不阻塞主路径。
4. 受限可配置：避免策略组合爆炸。
5. 分层单向依赖：符合 `awlf/document/architecture/分层与依赖规范.md`。

## 2. 成熟开源体系参考与迁移策略

| 参考体系 | 关键能力 | 迁移策略 | 不直接照搬点 |
|---|---|---|---|
| Zephyr（zbus/msgq/workqueue/poll） | 中断最小化、异步任务化、事件聚合等待 | 吸收执行上下文分离与事件化治理 | 不直接绑定 Zephyr 内核对象语义 |
| Linux（SocketCAN/lockless ring buffer/PREEMPT_RT） | 路由解耦、缓冲可观测、实时路径约束 | 吸收分层解耦与路径预算思想 | 不照搬 Linux 专用内核机制 |
| AUTOSAR（COM/PduR） | 路由层职责独立、配置治理 | 吸收职责边界与配置治理方法 | 不引入完整 AUTOSAR 配置体系复杂度 |
| ROS2/DDS（QoS） | 策略受限可配置与兼容性思路 | 吸收策略配置与兼容性审查理念 | 不直接引入完整 DDS 协议栈 |
| NATS（Pub/Sub + Req/Rep） | 流式与事务式模型并存 | 吸收双模型并存策略 | 不引入 NATS 服务端语义依赖 |
| libuv（event loop） | 异步执行统一治理 | 吸收统一执行器思路 | 不绑定特定事件循环实现 |

## 4. 设施清单与落地要点

## 4.1 数据结构设施（T3）

| 设施族 | 建设目标 | 工程要点 | 优先级 |
|---|---|---|---|
| 队列设施族 | 入口、分发、消费路径隔离与顺序保障 | 区分路径职责与退化策略，不单一队列硬承载全部场景 | P0 |
| 索引设施族 | 主题匹配、事务关联、订阅索引 | 明确索引一致性与容量上限治理 | P0 |
| 时间组织设施族 | 超时调度、周期扫描 | 统一时基与超时行为审计 | P0 |
| 资源设施族 | 句柄/槽位/对象生命周期治理 | 位图/池化等资源治理能力分层管理 | P1 |
| 统计设施族 | 计数、窗口、分位统计组织 | 指标采样与汇聚开销可控 | P1 |

工程原则：

1. 先冻结“场景职责”，后冻结“结构实现”。
2. 选型必须服务时延预算与可观测目标。
3. 禁止在规划阶段绑定单一算法。

## 4.9 设施归属划分（AWLF 补充 vs 通信中间件内部）

### 4.9.1 归属判定规则

1. 被两个及以上服务域复用，且不绑定通信语义的设施，归入 AWLF 基础设施。
2. 直接承载通信语义（主题、订阅、路由、可靠性策略）的设施，归入通信中间件内部。
3. 若设施同时具备“通用能力 + 通信特化策略”，必须拆分为“AWLF 通用基座 + 通信层策略封装”。
4. 归属判定优先保证分层单向依赖，不允许以复用为由打破边界。

### 4.9.2 需要在 AWLF 补充的基础设施

| 设施域 | 典型设施 | 推荐归属层 | 归属理由 |
|---|---|---|---|
| 运行时时基 | 单调时钟、统一 deadline 语义 | `lib/osal` | 所有实时模块共享，不能由通信层私有化 |
| 并发原语 | 原子与内存序、事件同步、等待唤醒 | `lib/osal` + `lib/sync` | 通用并发能力，需跨模块一致 |
| 通用队列/缓冲 | SPSC ringbuffer、通用对象池/句柄池 | `lib/core/data_struct` | 可被通信、驱动、控制算法共同复用 |
| 执行基座 | 统一任务执行器抽象（线程/工作队列、异步队列原语） | `lib/async` | 异步机制统一收敛，避免在 `lib/osal` 混入策略语义 |
| 通用观测基元 | 计数器、时延统计基元、轻量 trace 钩子 | `lib/osal`（当前阶段） | 观测先挂 OSAL，统一时间与平台后端；时间戳通过 OSAL 单调时钟接口输出，后端可接 `cpu_time(DWT)` |
| 配置与能力声明基元 | 配置校验框架、能力声明元信息容器 | `lib/core` | 面向系统级治理，不应被单一中间件绑定 |

### 4.9.3 由通信中间件内部实现的设施

| 设施域 | 典型设施 | 推荐归属层 | 归属理由 |
|---|---|---|---|
| 数据平面语义 | Topic 匹配、订阅索引、分发路由 | `lib/services/comm` | 直接体现通信语义，不具备通用复用价值 |
| 事务语义 | Req/Rep 关联、超时回收策略 | `lib/services/comm` | 是通信事务模型的一部分 |
| 策略语义 | 可靠性等级、背压策略、丢弃策略 | `lib/services/comm` | 与通信 QoS 策略强绑定 |
| 适配语义 | 总线接入适配契约与生命周期管理 | `lib/services/comm` + `adapter impl` | 属于通信核心与外设适配边界职责 |
| 通信观测语义 | 按 Topic/订阅者/路由维度的观测指标 | `lib/services/comm` | 指标维度与通信对象模型强绑定 |

### 4.9.4 边界收敛要求

1. AWLF 基础设施只提供能力，不携带通信业务语义。
2. 通信中间件不得绕过 AWLF 基座重新实现通用并发与时基能力。
3. 若发现“仅通信层需要”的设施被错误上提到 AWLF，应在评审阶段下放回通信层。
4. 若发现“多个模块都在重复实现”的设施，应评估上提至 AWLF。

### 4.9.5 当前阶段最小改动约束

1. 当前阶段新增 `lib/async`，用于承接异步执行机制；不新增 `lib/observe`。
2. 异步相关能力按“通用机制 + 业务策略”拆分：通用机制收敛到 `lib/async`，通信策略留在 `lib/services/comm`。
3. 通用观测先挂 `lib/osal`；对外时间语义统一使用 OSAL 单调时钟接口；`cpu_time(DWT)` 仅作为平台后端实现能力，不作为上层直接依赖。
4. 当观测能力在多个服务域稳定复用后，再评估从 `lib/osal` 拆分独立 `lib/observe` 的必要性。

## 5. 全面取舍总结（避免局部优化）

1. 不将基础设施收缩为“仅数据结构”。
2. 不将基础设施收缩为“仅 OS/SYNC/ASYNC 抽象”。
3. 必须把数据、控制、执行、观测、验证、治理作为一体化工程建设。
4. 必须先做设施边界冻结，再做接口与实现冻结。
